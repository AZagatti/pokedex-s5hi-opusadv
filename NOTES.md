- 2026-07-11: First Lighthouse run (mobile, local preview) came back Performance 69, LCP 13s — the CSR-only list page waits for JS to boot, fetch the list, then fan out 30 per-card detail fetches before the first card image can render. Fixed incrementally: switched grid cards from official artwork (100-200KB) to the small default sprite (~1-8KB), added eager/fetchpriority=high for above-the-fold cards, inlined per-route CSS (`inlineStyleThreshold`) to drop render-blocking stylesheet requests → Performance 76, LCP 6s. Remaining gap was structural (empty CSR shell + 30-request waterfall before first paint), so overrode `ssr=false` with `ssr=true` for just the "/" route so the first page of results (with a trimmed per-card projection, not full Pokemon objects) is baked into the prerendered HTML; a plain (non-$state) flag skips the mount effect's first run so it doesn't immediately wipe the seeded grid. Result: Performance 99-100, LCP ~1.3s, verified across repeated runs and confirmed via the `lcp-discovery-insight` audit that the LCP element really is the first card's image, eagerly loaded and discoverable in the initial HTML.
- 2026-07-11: Writing Playwright e2e tests surfaced a real concurrency bug: `applyFilters()`'s own initial-page load went through the shared `loadMore()` helper, whose `isLoadingMore` reentrancy guard exists to stop the scroll sentinel from double-firing. Changing filters quickly (exactly what automated clicking does) could start a new filter request while the previous one's detail-fetch was still in flight; the guard then silently dropped the new request's page load, leaving the grid stuck on "no Pokémon match" even though the `requestSeq` staleness checks were otherwise correct. Fixed by having `applyFilters` call `loadCandidatePage`/`loadBrowsePage` directly for its own first load, bypassing the scroll-only guard.
- 2026-07-11: Playwright fixture gotcha: a `test.use({ someArrayOption: [...] })` override on an `option: true`-style fixture gets merged via `Object.assign`, which spreads a bare array's elements as separate merge sources — RegExp instances (no enumerable own properties) then vanish into `{}` and the fixture silently stops being an array. Fixed by wrapping the array in a plain object (`{ patterns: [...] }`) so the override replaces a real object property instead of getting spread.
- 2026-07-11: First CI run failed: every e2e test hit `net::ERR_CONNECTION_REFUSED` even though the webServer's build/preview logs showed no errors. Root cause: Playwright's default webServer readiness check polls `localhost`, while the test baseURL used the literal `127.0.0.1` — on the GitHub Actions runner these apparently resolved to different loopback interfaces, so the readiness check could pass against one while real requests hit the other (refused). Fixed by binding vite preview explicitly to `--host 127.0.0.1` and pointing Playwright's own `webServer.url` at that same literal address. Second CI run was fully green.

- 2026-07-11: A second contrast-fix pass on the detail page's snapshot audit surfaced a third instance of the same bug: the evolution chain's "current" item badge (still on the un-fixed `--accent`) plus its nested `<small>` level text at `opacity: 0.75`, which dilutes contrast further on top of an already-borderline background. All of `/`, `/berries`, `/pokemon/[name]` (snapshot), `/favorites`, and the 404 page now score 100/100/100/100 where measurable.
- 2026-07-11: Committing the above fixes, lefthook's pre-commit `lint` job failed with "Expected at least one target file. All matched files may have been excluded by ignore rules" — every staged file that commit happened to be `.svelte`. Reproduced directly against the `oxfmt` binary (bypassing ultracite/lefthook entirely): `oxfmt --check <any-known-good-file>.svelte` always fails this way, even for a file `oxfmt --check .` (whole-project scan) confirms is correctly formatted. Worse than it first looked: `oxfmt --check a.ts a.svelte` (mixed args) doesn't fail, but silently checks only the `.ts` file and skips the `.svelte` one with no warning — so every earlier commit this session that staged a mix of `.ts` and `.svelte` files had its `.svelte` files pass the pre-commit hook without ever actually being checked, and this only surfaced now because this particular commit staged `.svelte` files exclusively. A real bug in `oxfmt` 0.58.0's explicit-file-argument path, not a problem in the files themselves. Fixed by changing the lint job to scan the whole project (`ultracite check .`) instead of `{staged_files}` — the only way to guarantee `.svelte` files actually get checked at all — negligible cost at this project's size (~250ms).
