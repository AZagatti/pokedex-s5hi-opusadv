- 2026-07-11: All 6 pages/features implemented, reviewed by subagents, and verified live via chrome-devtools MCP (list/detail/berries/favorites/theme/404). Found and fixed via live debugging: a Svelte 5 effect infinite-loop on the favorites page (reading+writing the same $state in one effect), a client-side-navigation remount bug on the detail page (fixed with `{#key pokemon.name}`), an evolution-chain flattening bug that lost branch topology (rewrote as a genuinely recursive component), incomplete ARIA tabs on the sprite switcher, invalid button-in-anchor nesting on cards, and low-contrast type badges (added a WCAG luminance-based text-color helper).
- 2026-07-11: Before wiring CI, verified the base-path (`BASE_PATH=/pokedex-s5hi-opusadv`) production build had never actually been loaded under that prefix — every prior screenshot/test ran at base `''`. Wrote `scripts/pages-emulate.mjs` (a tiny Node server mimicking GH Pages: serves `build/` under the base path, falls back to `404.html` with a real 404 status for unmatched paths) and confirmed assets, internal links, infinite scroll, search, and the hard-reload-on-deep-link SPA fallback all work correctly under the prefix.
- 2026-07-11: First Lighthouse run (mobile, local preview) came back Performance 69, LCP 13s — the CSR-only list page waits for JS to boot, fetch the list, then fan out 30 per-card detail fetches before the first card image can render. Fixed incrementally: switched grid cards from official artwork (100-200KB) to the small default sprite (~1-8KB), added eager/fetchpriority=high for above-the-fold cards, inlined per-route CSS (`inlineStyleThreshold`) to drop render-blocking stylesheet requests → Performance 76, LCP 6s. Remaining gap was structural (empty CSR shell + 30-request waterfall before first paint), so overrode `ssr=false` with `ssr=true` for just the "/" route so the first page of results (with a trimmed per-card projection, not full Pokemon objects) is baked into the prerendered HTML; a plain (non-$state) flag skips the mount effect's first run so it doesn't immediately wipe the seeded grid. Result: Performance 99-100, LCP ~1.3s, verified across repeated runs and confirmed via the `lcp-discovery-insight` audit that the LCP element really is the first card's image, eagerly loaded and discoverable in the initial HTML.
- 2026-07-11: Writing Playwright e2e tests surfaced a real concurrency bug: `applyFilters()`'s own initial-page load went through the shared `loadMore()` helper, whose `isLoadingMore` reentrancy guard exists to stop the scroll sentinel from double-firing. Changing filters quickly (exactly what automated clicking does) could start a new filter request while the previous one's detail-fetch was still in flight; the guard then silently dropped the new request's page load, leaving the grid stuck on "no Pokémon match" even though the `requestSeq` staleness checks were otherwise correct. Fixed by having `applyFilters` call `loadCandidatePage`/`loadBrowsePage` directly for its own first load, bypassing the scroll-only guard.
- 2026-07-11: Playwright fixture gotcha: a `test.use({ someArrayOption: [...] })` override on an `option: true`-style fixture gets merged via `Object.assign`, which spreads a bare array's elements as separate merge sources — RegExp instances (no enumerable own properties) then vanish into `{}` and the fixture silently stops being an array. Fixed by wrapping the array in a plain object (`{ patterns: [...] }`) so the override replaces a real object property instead of getting spread.
- 2026-07-11: First CI run failed: every e2e test hit `net::ERR_CONNECTION_REFUSED` even though the webServer's build/preview logs showed no errors. Root cause: Playwright's default webServer readiness check polls `localhost`, while the test baseURL used the literal `127.0.0.1` — on the GitHub Actions runner these apparently resolved to different loopback interfaces, so the readiness check could pass against one while real requests hit the other (refused). Fixed by binding vite preview explicitly to `--host 127.0.0.1` and pointing Playwright's own `webServer.url` at that same literal address. Second CI run was fully green.
- 2026-07-11: Enabled GitHub Pages via `gh api repos/AZagatti/pokedex-s5hi-opusadv/pages -f build_type=workflow` before the first push, so the Actions deploy job had a Pages site to land on. Pushed to `main`; CI (lint, typecheck, unit+e2e, then build+deploy) went green end to end. Verified the live URL (https://azagatti.github.io/pokedex-s5hi-opusadv/) loads with no console errors, infinite scroll/search/detail navigation/hard-reload-deep-link all work, and a mobile Lighthouse run against the live URL scored Performance 100, Accessibility 100, Best Practices 100, SEO 100 (LCP 1.6s).
- 2026-07-11: Before declaring done, checked Lighthouse on routes other than "/" (never measured before). `/pokemon/charizard`'s navigation-mode audit failed outright (`ERRORED_DOCUMENT_REQUEST`, 404) — expected, since GitHub Pages serves it via the `404.html` SPA fallback with a real 404 status; Lighthouse refuses to audit a non-200 main document regardless of the page's own quality. Verified performance instead via a client-navigation trace (INP 22ms, CLS 0) and a11y via `mode: snapshot` (sidesteps the reload). That snapshot audit found two real, small a11y bugs: the sprite-switcher active tab / hidden-ability tag's white-on-accent text was 4.24:1 contrast (just under WCAG AA's 4.5:1 for small text), and the cry button's aria-label ("Play charizard's cry") didn't contain its visible text ("Play cry") as a substring, which breaks voice-control matching. Fixed both (a shared `--accent-text-bg` darkened variable; reordered the aria-label), and applied the same contrast fix to the list page's active type-filter chips (same hardcoded-white pattern already known to be risky from the earlier type-badge fix). `/berries` also had a real, fixable gap: Performance 88 (LCP 3.1s) since it's pure CSR with no dynamic param at all — applied the identical `ssr=true` override used for "/", and since this page has no client-side re-fetch to guard against, the fix was a one-line addition. Performance 100, LCP 0.7s afterward.
